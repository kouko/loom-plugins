## Problem
目前 agent 遇到 CLI 拒絕或失敗時，部分結果已有處理建議，部分只有原因；建議的位置與寫法也不一致。agent 必須從不同訊息自行尋找後續處理方式，現有輸出沒有一致說明哪些是判定依據、哪些只是建議。

## Proposed outcome
建立共同的下一步建議原則，先讓相容性與審查人數兩個已採用 JSON 的流程，在遇到問題時以一致方式提供與原因相符的後續處理建議，同時維持判定、建議與授權之間的區別。

## Acceptance
1. 全體 CLI 的下一步建議原則與分批範圍可核對，清楚區分首批已交付流程、既有建議及未遷移介面，不宣稱全部命令已完成統一。
2. 相容性與審查人數兩個流程的已知拒絕及錯誤能提供與原因相符的處理建議；沒有可靠修復方式時保留未知並指出可查證事項，不編造修復或宣稱可直接繼續。
3. agent 能區分工具判定與後續建議；建議的有無或內容不改變原結果、既有拒絕或必要授權，不觸發自動執行、重試或文字備援。
4. 既有判定、退出碼、已發布必要資料欄位、審查政策、授權、宿主信任及遠端操作查證行為保持相容；首批建議不引入新的寫入副作用，也不破壞既有下一步建議。
5. help、流程說明及獨立 dogfood 證據符合首批實作，涵蓋正常、明確拒絕與錯誤，並清楚揭露沒有建議或尚未驗證的情況。

## Constraints
- 使用者要求先合併 PR #155，再討論並實作統一下一步建議；PR #155 已合併，既有 worktree 與證據保留。
- 延續「全體規劃、分批交付」。
- 建議不構成執行、發布、合併或宿主信任授權。
- 使用者確認以 `Suggested next step:` 作為文字標籤、`suggested_next` 作為 JSON 欄位，強調它是建議。
- 不以統一建議本身宣稱 agent 成功率、速度、成本或 token 改善。

## Out of scope
- 全部命令一次遷移，或新增其他命令的 JSON 模式。
- 可直接執行的操作清單、通用重試、自動修復或全面故障恢復框架。
- 改變原有業務判定、發布／合併政策或宿主 hook 協定。
- 既有使用者資料遷移、已安裝 plugin 更新及付費外部模型呼叫。
