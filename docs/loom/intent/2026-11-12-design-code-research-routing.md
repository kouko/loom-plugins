## Problem

kouko 在 dotfiles 的工程討論中，遇到 agent 未比較重要替代方案便推薦工具，
被追問後又在沒有新增比較依據時改變推薦，保存的研究紀錄也沒有同步。
目前雖有工程研究方法，設計階段缺少自己的研究能力；各階段何時需要研究、
由誰評估與承接結果仍不夠明確，不能只靠使用者追問才補足分析。

## Proposed outcome

loom-design 與 loom-code 各自提供責任清楚的研究技能，支援設計與工程決策。
各階段能依當下問題、已有證據及決策影響，判斷是否需要研究，並在研究後
將結果或仍未解決的不確定性帶回原任務。重要方案的比較及結論有可回查的依據，
不因未使用研究技能而省略必要判斷，也不因進入某一階段就一律展開研究。

## Acceptance

1. loom-design 與 loom-code 各自的研究技能可被發現與使用；代表性的設計及工程問題能交由適當研究能力處理，責任差異可由實際行為辨識。
2. loom-code 各階段在代表性案例中，能對會影響決策的證據缺口展開適當研究，對已有足夠適用證據或不影響決策的問題避免不必要研究；判斷與實際行為可被核對。
3. 設計階段在代表性案例中能適當使用自己的研究能力；研究結果回到原任務時保留既定目標、使用者決定及授權範圍，不自行代替使用者確認或推進決策點。
4. 重要方案選擇能依問題採用相關評估維度與共同標準，區分必要條件、偏好、事實及未知；未取得足夠比較依據時，不把候選方案說成已證明較佳。
5. 研究後的結論、限制及來源可回查；同題追問或改變推薦後，保存紀錄與對話中的最新結論保持一致，條件改變時保留原有決策依據。
6. 上述分工、觸發、不觸發、返回原任務及追問後更新紀錄，有可重查的實際行為驗證，不能僅以規則文字存在、技能被讀取或檔案格式正確作為成立證據。

## Constraints

- kouko 已確認：將研究方法、評估與紀錄維護的複雜度留在各自的研究技能，原有階段流程盡量維持簡單。

- 採用 kouko 選定的方向：loom-design 與 loom-code 各自有研究技能，責任分開；同時規劃 loom-code 各階段如何判斷是否觸發研究。
- 評估維度與方法依問題需要選用，不把八個維度或完整研究流程一律套用於每個階段。
- 保留既有 Loom 的階段與使用者決策界線；研究不能自行擴大原任務授權。
- 遵守專案現有的 plugin 可攜性與依賴界線，不跨 plugin 讀取對方的內部檔案。
- 保留既有研究、試驗及其限制，不以本次規劃覆寫先前結果或宣稱已證明新機制有效。

## Out of scope

- 實作 dotfiles 的 RAR 轉 ZIP 功能或修改其設定與原研究紀錄。
- 自動更新使用者既有 plugin 安裝、個人設定或 Obsidian 筆記。
- 新增背景研究、排程服務或額外使用者決策點。
- 保證每次模型執行必然正確觸發研究，或宣稱單一案例能證明所有模型與宿主的品質改善。
- 自動合併本次變更。
