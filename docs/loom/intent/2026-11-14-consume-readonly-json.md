## Problem
目前十六個 CLI 子命令混用文字與可選 JSON 結果；相容性檢查與審查人數計算雖已提供 JSON，正式流程仍使用文字呼叫。agent 尚未在這兩個流程中一致地使用並驗證明確資料欄位；只讓輸出可解析，也不足以辨識版本、型別或結果含義不符。

## Proposed outcome
先處理介面一致性的已知缺口：保留全體命令盤點與分批方向，讓相容性與審查人數兩個正式流程實際使用並驗證已發布 JSON，同時保留必要錯誤辨識與現有安全界線。

## Acceptance
1. 全部十六個子命令的一致性盤點與分批方向可核對，清楚區分首批已交付範圍、必要模式差異及尚未遷移的命令。
2. 相容性檢查與審查人數判讀的正式流程採用已發布的 JSON 資料，能依明確欄位決定是否繼續及所需獨立審查人數，不依賴成功訊息的散文格式。
3. 首批消費流程能在使用結果前驗證支援版本、命令、必要欄位、型別與退出碼／結果含義的一致性，容忍相容的額外欄位，拒絕不完整、矛盾或不可解析的結果，不把明確拒絕或結果未知當成成功。
4. 既有文字呼叫、已發布 JSON 結果、判定與審查政策、授權、宿主信任及現有操作結果查證行為保持相容；首批驗證不引入寫入副作用。
5. help、流程說明與獨立 dogfood 證據符合首批實作，涵蓋正常、明確拒絕及格式／執行錯誤，揭露未驗證界線，不以盤點完成冒稱全體工具已遷移。

## Constraints
- 使用者選擇：「全體規劃、分批交付」。
- 使用者於比較介面一致性與恢復成本後選擇：「先處理一致性的缺口 吧」。本輪為一致性首批交付，不是全面故障恢復專案。
- 一致性以判讀與驗證原則為主，不強迫全部命令回傳完全相同的 JSON。
- 保留現有 worktree 與驗證紀錄。
- 不以 JSON 格式本身宣稱速度、成本或 token 改善。
- 保留必要診斷與現有恢復處理，不承諾任意 Loom 錯誤都不中斷。

## Out of scope
- 改變工具原有的業務判定、發布／合併授權或宿主 hook 協定。
- 真實使用者資料遷移及與介面一致性無關的工具功能。
- 新增其他命令的 JSON 模式、自動文字備援、通用重試或全面自動恢復框架。
- 自動更新已安裝 plugin、呼叫付費外部模型，或繞過既有拒絕與授權。
