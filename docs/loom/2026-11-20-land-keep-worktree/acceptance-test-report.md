## 對你既有的資料做了什麼

這個變更改的是合併後要不要刪掉你的 worktree 與分支。沒要求保留時，刪除的東西和以前完全一樣（第 3 條）；要求保留時，刪得比以前少，什麼都不刪。清理指令遇到 worktree 裡有沒存的修改會拒絕，不會強制丟掉。這次測試只在暫存資料夾裡的測試倉庫上進行，沒有碰到你真正的倉庫、分支或 GitHub。

## 我替你決定的事

- **保留選項只能和「驗收合併」一起用** — 我選擇把它用在清理或批次清理上時直接報錯，而不是默默忽略，因為忽略會讓人以為有保留。之後要放寬只需改一處判斷。
- **保留時主幹仍照常同步** — 主幹同步和 worktree 是兩件事，同步是一般合併的一部分，所以保留時照做。若你其實希望保留時連主幹都不動，之後要多加一個選項。
- **保留時不印「接下來切換到哪個資料夾」那一行** — 因為 worktree 還在，agent 就留在原地繼續用。
- **不另外記錄「這個變更被保留了」** — 保留下來的變更就是一個普通的已合併變更，既有的清理與批次清理照常能處理它；代價是批次清理應該也會把它列進可清理的清單（我沒有實際試；不論如何仍要你同意才會刪）。
- **ship 流程文字和說明文字各改一處** — 這是 agent 執行合併前會讀的兩個地方。
- **版本號升一個次版本（3.88.0）** — 因為新增了一個指令選項。

## 我不確定你要不要的事

- 如果你的 GitHub 倉庫開了「合併後自動刪除分支」的設定，即使加了保留，GitHub 自己還是會把遠端分支刪掉（說明文字已寫明這一點，本機也無法重現）。這樣可以接受嗎？還是要在這種倉庫上先提醒你？
- ship 流程文字在「合併後出錯」那段，先寫「執行清理」，下一句才寫「如果有保留就不要清理」。只讀前一句的 agent 可能會先照著清理。要不要把保留的例外移到前面？
