## 對你既有的資料做了什麼

沒有。這個變更只改了指引文字、檢查工具的判斷，以及一行拒絕訊息；沒有讀寫你既有的任何紀錄。檢查工具這一輪變得比上一輪嚴格（拒絕不跑測試的選項和不認得的選項），所以理論上，先前某個用了這類選項的審查證據重新檢查時可能被拒；但這些選項本來就沒有真的跑測試，被拒是對的，也沒有需要搬移或備份的東西。

## 我替你決定的

- **第 1 條在檢查工具本身驗，而不是跑一整輪 closing review** — 我直接呼叫 closing review 和審查證據檢查兩處共用的那個判斷，用 38 種指令逐一比對。理由是這樣才能同時看到「該接受的接受了」和「該拒絕的仍拒絕」；完整跑一輪要另開一個變更。若你要求端到端，代價是再多跑一輪 closing review。
- **第 1 條：檢查工具只接受它認得的選項** — 修正採用「只放行清單上的選項」，所以像平行執行或輸出測試報告檔這類正常但不在清單上的選項，現在也會被拒。這是寧可錯拒、不可錯放的取捨；若你常用這類選項，要再把它們加進清單。
- **第 2 條的範圍比你寫的寬** — 指引是對「所有什麼都沒打破的攻擊」都要求指名既有測試，不只限於需要實際執行程式的變更。我判為 works，因為它涵蓋了你要的情況；若你只想在需要時才這樣做，要再改一次指引文字。
- **第 4 條的範圍比你的原文窄** — 你寫的是「只有刻意破壞規則的人才會觸發」；修正把它限定在「刻意繞過 loom 自己的內部規則」，而外部輸入就能觸發的問題，即使是刻意攻擊的人才會做，也維持原嚴重度、要修。我判為 works，因為你當初要解決的正是「繞過內部預算」那類發現被修掉、讓變更變大的問題；但如果你原本也想把刻意攻擊者的發現評為 nit，這裡就和你想的不同。
- **Plugin 沒有實際裝進 Claude Code 試** — 我用 repo 自己規定的驗證方式（suite 加 manifest 檢查）確認變更能在乾淨副本載入；指引文字類的條目是讀 agent 實際會讀到的原文。
- **主 agent 沒有駁回任何 important 以上的發現。**
