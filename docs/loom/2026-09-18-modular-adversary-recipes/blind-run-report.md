## 我替你決定的事

- **「新增一種」到底算幾份檔案** — 你的驗收寫「一份檔案加一行」，但另一條
  驗收又說「每一份配方有自己的測試檔案」。這兩句話對不起來。專案的做法是
  讓前者贏：新增一種時沒有任何檢查要求你補測試檔。代價是——你加的新配方，
  它寫了什麼沒有人盯著，之後被人改掉或刪掉都不會有人喊。要改成「加一種就得
  補測試」的話，新增就變成兩檔一行。
- **「移除一種」到底算幾步** — 實際是三步（配方檔、對照表那行、那一種自己的
  測試檔），你的驗收寫兩步。我照兩步做過，檢查是紅的。我判定為「你要的結果
  達成了、但步數描述要修」，而不是判它不成立。如果你認為驗收的字面就是合約，
  這條該算不成立。
- **技能和關卡合用一份配方** — 這是拆分前就有的樣子，這次沒有拆開。
  後果是：如果哪天你只想拿掉「關卡」而留下「技能」，那不是刪一份檔案，
  而是要動那份合用檔案的內容——也就是這次修改想消滅的那種操作。
- **我用什麼代表「一次修改」來試** — 我挑了三種來試新增（地圖、計畫、證據），
  沒有把七種沒有配方的都試一遍。專案自己的對抗測試把七種都試了，而且那
  七種確實就是目前沒有配方的全部，這點我核對過，它沒有誇大。

## 交付物的語言與格式

| 東西 | 應該是英文 | 實際 | 另有格式規定 | 符合 |
|---|---|---|---|---|
| 計畫書 | 是 | 英文 | 無 | ✅ |
| 規格書 | — | 這次沒有規格書（不是產品面的修改） | EARS 編號 | 不適用 |
| 審查意見 | 是 | 英文 | 標籤格式 | ✅ |
| 證據與紀錄 | 是 | 英文 | 無 | ✅ |
| 測試說明文字 | 是 | 英文 | 無 | ✅ |
| 測試名稱 | 是 | 英文 | 三段式命名 | ⚠️ 見下 |
| 提交訊息 | 是 | 英文 | 無 | ✅ |
| 這份報告 | 否（用你的語言） | 繁體中文 | 無 | ✅ |

測試名稱那一欄：名字都是英文、也都讀得懂，但寫法是「一句話」而不是規定的
「三段式」。例如「每一份配方都保持形狀」這種寫法，切不出「哪個東西／什麼
狀態／該有什麼結果」三段。這不影響功能，是規格一致性上的小落差。
（例：`test_every_recipe_keeps_the_shape`、`test_adding_any_unrouted_kind_keeps_the_shape`。）

## 我不確定你想不想要的事

1. **新增一種時，沒有人逼你補測試。** 這是為了讓「加一種＝一檔一行」成立而
   刻意放掉的。好處是新增真的很輕；壞處是新加的配方寫了什麼沒有人守著，
   它跟今天那三份「每個字都被盯著」的配方，保護程度不一樣。你要不要這個不
   對稱？

2. **「共用文件不准夾帶某一種的私有規定」只擋得住有寫出種類名字的句子。**
   我試過：把一條只對規格書成立的規定寫進共用文件，句子裡有「規格書」這個
   詞——被抓；把同一條規定換句話說、避開那個詞（改寫成「有編號要求的那種
   文件」）——完全沒人擋，檢查全綠。這個限制在檢查自己的說明裡有寫清楚，
   不是藏起來的，而且沒有任何檢查能真的擋住換句話說。你需要知道的是：
   這道防線擋得住手滑，擋不住決心。

3. **這條分支為了這件事寫了將近四千行測試。** 被搬動的散文大約 60 行，新增的
   導航文字大約 26 行，而新加的檢查程式在 3900 行上下，另外還有一支 622 行的
   對抗測試。這些檢查我一一驗過，確實都在做事（我每一次破壞它們都抓到了）；
   但你中途問過「這條分支有沒有帶不必要的測試」，這個比例就是答案的素材。
   我是見證者不是審查者，不替你下判斷，只把數字放在這裡：其中有幾支是
   「檢查別的檢查有沒有寫對」的第二層測試（例如一支 287 行的檢查，專門確認
   那四條性質每一條都真的有人在擋），那類是最值得你問「需不需要」的。

4. **移除的那一條驗收文字要不要改成三步。** 見上一節。

5. **這次修改自己帶的那支對抗測試，現在是紅的。** 這是我在這次盲跑裡發現的
   唯一一個「現在就壞著」的東西，而且它不是我弄壞的——我只是照原樣把它跑完。
   二十個案例裡十九個過，一個沒過，而且重跑一次結果一模一樣。
   沒過的那個案例在做這件事：把某一份配方裡最長的那句話換個說法，然後看
   那一份自己的測試會不會因此變紅。換規格書那份、換技能與關卡那份，都變紅了；
   **換程式碼那份，什麼都沒發生**。於是那個案例自己宣告：這句話沒有人在盯。
   我自己追了一次，情況比那句宣告細緻一點：那句話的**意思**是有人盯的——
   我把它整句反過來寫（從「要跑，並回報存活的變異」改成「可以跳過，那種報告
   沒人看」），程式碼那份的測試立刻變紅。真正的落差是：盯的方式只認得
   那句話的後半段，所以改前半段的措辭不會被發現。
   對你的意義有兩層。第一層：這支測試在交付前是會被執行的，它現在紅著，
   代表這個修改以目前的樣子還不能算通過自己的關。第二層，也是比較值得想的：
   「改一份配方，它自己的測試會抓到」這件事，對那一句話只成立一半——
   反過來寫會抓到，換句話說不會。你要不要求把那句話盯緊，或是接受這個程度，
   是你的決定；但紅燈本身要先處理掉。
   （另外順帶修正我自己的一個誤判：我中途以為這支測試跑不完、遠超紀錄上寫的
   十一分鐘。跑完之後實測 10 分 24 秒，紀錄上的數字是準的。）
