# 讓 loom 做出邊界明確、入口少的模組 — 我試了什麼、結果如何

2026-10-05 在專案的乾淨副本上試。第一輪測的是 b6dc33e9，修正之後重測的是 5dd3f96d。每一條怎麼試、回來什麼：`docs/loom/2026-10-05-deep-module-boundaries/evidence/acceptance-test-evidence.md`。

開始前先確認這個版本能被載入：在修正後的乾淨副本上，plugin 設定檔驗證通過，各平台設定同步檢查也通過。

這次修正改了三處規則文字：

- 「每個 task 都要寫明入口」現在只要求改到正式程式碼（非測試程式碼）的 task。
- 直接測內部、而入口已有測試涵蓋同樣行為的測試，修法改成直接刪掉，不再改寫成另一支入口測試。
- 跨模組共用的抽出，要放進一個自己的模組，呼叫它的模組從那個模組的入口引用。

第 1、2、4、5 條會受這次修正影響，我已全部重測。第 3 條沒有受影響，沿用第一輪的結果。

第 1、2、4 條的試法：我在一個假想的小型商店程式上編了範例改動和 plan task，先寫好「應該被抓／不該被抓」的答案，再交給全新的 LLM reviewer 判，它們只能讀這次修正後的規則文字。重測時一共用了 12 個審查範例和 8 個 plan task，新增的是「只改測試的 task」「只改版號與 CHANGELOG 的 task」「入口已涵蓋時要刪掉的內部測試」「把共用程式放進別的模組當私有函式」這幾種。審範例改動的有兩位 reviewer，用的是不同 model、各自獨立判，兩位的結果都和答案完全一致。

## 我替你決定的事

- **規則只寫在 plan 指示裡，不另寫進工程基本規範**：寫 plan 的人照規則標入口，判斷交給審查端。代價是偶爾可能多一輪修正。要改的話，在基本規範補一句即可。
- **四條審查規則改在既有的四列裡，不新增審查項目或檢查代號；20／50 行與三次的數字保留，只從「判定」改成「提示」**：這是照你在範圍外的決定。要改數字本身，需要另開一次改動。
- **版號升 minor（3.34.0）而不是 patch**：因為改的是站點指示。改回 patch 只影響版號字串。
- **把抓到「入口定義會繞圈」的那支對抗測試正式收進測試套件**：依 repo 的測試位置規則，放在既有的測試資料夾。拿掉它，代價只是少一道防護。
- **第 1、2、4 條交給全新的 LLM reviewer 判，不是我自己判**：我知道答案，自己判會失準。限制是：這些都是玩具範例，每次只套用個別規則列，不等於在真實改動上跑完整一輪 closing review。
- **安裝那一步只做了驗證、沒真的裝**：照 README 安裝會從 GitHub 裝已發布的版本，並動到你本機的安裝，所以改用 plugin 驗證工具檢查這個分支的副本。
- 沒有任何被駁回的 important 以上的審查意見。
