## 我替你決定的

- **用乾淨副本直接跑檢查工具，而沒有把這個分支裝成 plugin** — 因為說明文件的安裝方式只會裝到已發佈的舊版，而改你的 plugin 設定不是我該動的。之後要改成「實際安裝後再試」，就是在發佈後重跑一次這份驗收。
- **範例 repo 的 jest、vitest、mocha、rspec、phpunit、Maven 相依套件都裝在暫存資料夾** — 照指示不碰你的環境；代價是只試了今天抓到的最新版（例如 jest 30、vitest 5、phpunit 13），舊版沒試。
- **go、deno、bun、cargo 的任何子指令都歸它自己那一列判斷，不跑測試的子指令直接拒收**（修正時代為決定的，回答上一輪的第一個疑問） — 代價是這幾個工具以後若有別的「跑測試」寫法，不能靠 reviewer 確認放行，只能改工具。
- **比對 reviewer 引用的輸出時忽略秒數，測試數量仍要一字不差**（修正時代為決定的，回答上一輪的第二個疑問） — 這樣 Maven 這類每次秒數都不同的輸出不會再被誤擋。代價是：同一份內容的另一次執行，只要測試數量相同，它的引用現在也會被接受；擋住「別的執行」靠的是內容必須相同、數量必須相同，而不再是每個字元都相同。
- **清單上的工具輸出讀不懂時，改由 reviewer 確認而不是直接拒收**（設計時代為決定的） — 代價是框架改輸出格式時要多一次 reviewer 確認，而不是被擋死。
- **Rust 的找漏洞測試必須搬進專案的 tests 資料夾才能記錄**（設計時代為決定的） — 因為 cargo 只會跑那裡的測試檔。
- **兩件事留到之後處理（都沒被評為 important）** — 審查證明裡的檔案路徑若含 `../` 目前會通過檢查（這次沒改到那段，會另開案）；`env` 開頭或 `npx --yes`、`pnpm jest` 這類寫法不在清單上，會走 reviewer 確認。
