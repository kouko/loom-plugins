## 我替你決定的

- **用乾淨副本直接跑檢查工具，而沒有把這個分支裝成 plugin** — 因為說明文件的安裝方式只會裝到已發佈的舊版，而改你的 plugin 設定不是我該動的。之後要改成「實際安裝後再試」，就是在發佈後重跑一次這份驗收。
- **範例 repo 的 jest、vitest、mocha、rspec、phpunit、Maven 相依套件都裝在暫存資料夾** — 照指示不碰你的環境；代價是只試了今天抓到的最新版（例如 jest 30、vitest 5、phpunit 13），舊版沒試。
- **「不跑測試的子指令」交給 reviewer 而不是直接拒收**（設計時代為決定的） — 清單只認得 `go test`、`bun test` 這種「跑測試」的指令名稱；同一個工具的其他子指令被當成「清單外」，靠 reviewer 判斷。這就是第 3 條只算 partly 的原因。
- **清單上的工具輸出讀不懂時，改由 reviewer 確認而不是直接拒收**（設計時代為決定的） — 代價是框架改輸出格式時要多一次 reviewer 確認，而不是被擋死。
- **Rust 的找漏洞測試必須搬進專案的 tests 資料夾才能記錄**（設計時代為決定的） — 因為 cargo 只會跑那裡的測試檔。
- **reviewer 的確認必須逐字等於這次執行的某幾整行輸出**（設計時代為決定的） — 這擋住了沿用別次執行的確認，但也帶來下面第二個疑問。
- **兩件事留到之後處理（都沒被評為 important）** — 審查證明裡的檔案路徑若含 `../` 目前會通過檢查（這次沒改到那段，會另開案）；`env` 開頭或 `npx --yes`、`pnpm jest` 這類寫法不在清單上，會走 reviewer 確認。

## 我不確定你要的

- `go vet`、`deno check`、`cargo build`、`bun build` 這類同一工具「不跑測試」的指令，你要工具直接拒收（跟 `vitest list` 一樣），還是維持現在交給 reviewer 判斷？
- Maven 與 Node 唯一能證明「測試有通過」的那一行帶著執行秒數（例如 0.013 秒、0.016 秒），每次跑都可能不同。reviewer 照規定引用這一行時，最後一次重跑若秒數變了就會被拒收，而且會被當成要退回 Build 的新一輪（同樣的 Maven 指令連跑五次，出現了 0.013、0.014、0.016 三種秒數；我的一次測試就因此被拒收）。你要工具比對時忽略秒數，或是要 reviewer 改引用不帶秒數的行，還是接受偶爾多一輪？
