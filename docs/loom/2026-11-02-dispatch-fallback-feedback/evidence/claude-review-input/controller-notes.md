# Controller interventions and comparison limits

This is an exploratory small workflow experiment, not a randomized causal A/B benchmark. Fresh executors received only their assigned bundle, packet and hand-off. The controller did not instruct an expected file action. Execution stopped before Ship. Exact dispatch messages remain in the current conversation's tool record; no historical session contents were supplied.

## Preparation corrections

- The first missing-result baseline run had a genuine reviewer finding: the plan did not mark the called module entry. It recovered through Build and same-reviewer Round 2. The five not-yet-started fixtures received the same plan-entry clarification before execution; no app-code change was added by that clarification.
- Before either graduated test trial started, direct-suite bootstrap fixtures were superseded by active repos with an actual committed RED store probe, actual failed run, corrected function and real Git move into the suite. Old setup repos and packets remain explicitly excluded from the active trials.
- Both bundles have byte-identical runtime code. Candidate differences are only two prose passages. The source checkout and local origin/main were both 55587449a0473697dee852f0dff69b240ef5d36e.

## Execution scheduling and host issues

- To stay within four active native slots, some reviewer dispatches were sequential. One stale-program candidate executor's idle capacity wait was interrupted and then resumed without changing HEAD or resetting the review episode.
- A reviewer initially resolved a Python without pytest. An existing interpreter with pytest was provided; no package was installed.
- The stale baseline run completed finalization, commit and attestation validation, but its report-writing command hit a local guard while quoting an earlier guard rejection. It stopped after the second guard encounter. Root transcribed its final structured return as executor-return.json and separately inspected committed state. This file is explicitly not an executor-authored result.json.
- The stale baseline executor's final prose suggested incomplete privacy-scan trace for its final evidence commit. **Resolved by raw evidence:** command-log.jsonl line 26 records the actual scan of attestation-message.txt with exit 0; line 28 records the subsequent commit. Root independently re-read those entries after the auditors flagged the inconsistency. Do not infer a missing scan from the executor's inaccurate prose; the raw journal establishes execution. Mechanical attestation success alone still does not prove every process requirement.

## Newly exposed feedback gap

- In the graduated baseline trial, reviewer two self-disclosed historical probe replay outside its packet's allowed execution scope. The controller required exclusion of that review and protocol-respecting replacement at the same digest, with genuine conforming reviews rather than a synthesized PASS.
- Replacement feedback could not encode the unknown inherited profile. The controller required STOP, no new-task relabeling to evade feedback and no invented portable model. A previously generated but uncommitted attestation remains explicitly excluded; it is not a deliverable.
- The final candidate trial received an explicit reminder to stop if required feedback cannot represent unknown inherited state and to use historical RED evidence read-only. Its executor interpreted the shared contract as requiring feedback for every completed review, even successful review without pending retry, and exercised that path. This reminder is an in-flight protocol clarification, not a difference in the candidate skill's runtime code.
- Root independently reproduced feedback rejection for both success and replacement in both identical runtime bundles. Thus the core schema gap is independent of the A/B reminders, but counts of completed trials cannot be interpreted as candidate wording effects or model failure rates.

## Required reporting distinction

Report separately: actual test file actions; checker executions; committed attestation validity; semantic reviewer conformance; known guard/runtime/fixture deviations. Four mechanically completed records must not be called four perfectly conformant full workflows. A structurally valid uncommitted attestation with a known disallowed review must not be counted as a completed run. Do not claim activation, complete seven-station lifecycle, Claude/OpenCode behavior, population failure rates, or pinned model identity.
