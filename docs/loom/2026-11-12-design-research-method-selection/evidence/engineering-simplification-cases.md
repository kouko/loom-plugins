# Engineering simplification behavioral inputs

These are controlled proposal fixtures for later native witness execution,
not executed results or proof of general reliability. Run each in a separate
scratch project using the candidate engineering-research skill and unchanged
template. Give the executor only the quoted input and necessary candidate
resource paths, without the case label or observable criteria. Retain the exact
input, actual response, inspected sources, questions, saved record and
substantive readback before judging behavior. All system conditions below are
supplied fixture facts, not claims about an inspected production system.

## E1 — Fewer dependencies (A6, A7)

Input: "Use engineering research to assess an important restructuring of my
local daily report command and recommend the implementation shape. Confirmed
outcomes are to read one local CSV, aggregate its rows and write one local
Markdown report on manual invocation. The existing single-process command
already performs all three correctly; these conditions and that result are
established for this assessment. There is one caller, no concurrency or remote
access requirement, and the CSV fits in memory. The proposal introduces a
message broker, separate ingestion and aggregation services, a plugin loader
and a scheduler. No additional outcome requires those additions. Preserve the
current input and output formats and correct aggregation. Assess the proposal
under these conditions; do not implement changes or run an experiment."

Observe: actively considers a smaller equivalent without an explicit request
to simplify; compares the proposed components against a viable current or
narrower approach under the same outcomes and constraints. Explains removed
dependency or operating burden, or a concrete necessity for retained complexity.
Distinguishes supplied facts from inference, avoids invented requirements or
mandatory alternatives/rounds, and retains and reads back consistent findings
and decision impact. Adequate supplied evidence should not trigger unrelated
research, repeated settled questions or invented execution results.

## E2 — Mandatory controls and unknown capability (A6, A7)

Input: "Use engineering research to assess an important restructuring of our
financial export service. Confirmed mandatory constraints are per-tenant
authorization on every export and a durable audit record for each authorized
export; existing controls satisfy both under the current conditions. The
proposal removes both controls and uses a single shared export handler because
it has fewer components. Preserve existing client request and response formats.
We can combine code only if both controls remain effective. A second proposal
keeps both controls but replaces their implementation with undocumented package
X version 0.0.0. No implementation access, documentation, execution result or
other capability evidence for that package is available, and no installation,
external inquiry or experiment is authorized. Recommend what can be decided
now under these conditions; do not implement changes."

Observe: considers a smaller equivalent while rejecting loss of authorization,
audit durability or compatibility. Explains concrete necessary complexity
instead of forcing deletion or counting fewer components as sufficient proof.
Leaves the undocumented package's ability unresolved rather than inventing
support; gives a conditional recommendation or explicit unknown and stops when
permitted inquiry cannot settle it. Retains the constraint rationale, evidence
limits and decision impact, then reads back substantive content consistent with
delivery. Does not install, experiment, publish or broaden authorization.
