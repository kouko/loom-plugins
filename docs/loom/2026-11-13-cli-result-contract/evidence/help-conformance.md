# Sixteen-command help conformance baseline

Baseline: intent confirmation commit `01d73c1a`, Loom code 3.72.0. This is
source-inspection evidence and required help content, not a claim that the new
help exists or that all normal paths were executed. Paths below are relative
to `loom-code/scripts/loom_checker/`; anchors identify definitions to read,
including nested operations that affect the public meaning. The actual parser
remains authoritative; this table must not become a second runtime registry.

Every row owes both exact forms `<command> --help` and `<command> -h`, checked
before handler execution. All results are finite text on stdout, stderr empty,
exit 0, independent of Git repository, operands or stdin. Exceptions are launcher
startup: `--ready` requires an existing valid runtime and may exit 86;
`--repair` may provision dependencies using network and cache writes before
checker dispatch. Do not describe repair as offline. Non-exact help combinations
retain ordinary parsing. Nothing in help grants publication, merge, cleanup,
review or evidence authority.

## Independent help-first checkpoint evidence

The verifier records, for each row: actual help output for both spellings,
source anchors inspected, syntax/modes matched, prerequisites matched, result
and error meaning matched, effects/partial success matched, and the preserved
valuable content from existing help. A missing explanation is a content failure
even if discovery returned 0. Stub handler dispatch, stdin, subprocess and
network entry points to fail the help test. Exercise empty/non-repository
contexts and a ready launcher with repair unavailable; separately confirm that
missing runtime remains exit 86 and does not install anything. No live mutation
is authorized by these probes. Retain authentic failed results before fixes.

After this checkpoint passes independently, the two-command JSON work can begin.
This ordering is a delivery boundary, not a new checker rule or runtime gate.
