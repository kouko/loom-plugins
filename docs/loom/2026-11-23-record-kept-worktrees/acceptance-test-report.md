## 對你既有的資料做了什麼

用 `--keep-worktree` 合併時，loom 會在這個 repo 自己的 git 設定裡多寫一筆「這個分支是刻意保留的」紀錄（記在 repo 的設定，不在任何 worktree 的檔案裡，也不會被 commit 或推到遠端）；保留的 worktree 內容完全沒變。清理一個變更時，loom 現在會順手把該分支在 git 設定裡的整段設定刪掉，即使本機分支早已不在；以前只有在刪本機分支時才會刪這段（而刪本機分支本來就會一起帶走它），所以只有「本機分支已不在、設定卻殘留」這種少見情況會多刪一段殘留設定。3.88.0 時期保留、沒有紀錄的 worktree 不受影響、也不會被補記。

## 我替你決定的

- **用全新程序模擬「新的 session」** — 每次 land 都是獨立的程序，彼此之間只共用 repo 本身，藉此證明紀錄是從 repo 讀出來的、不是記在對話裡。真正的 GitHub 合併和查詢用假的回應代替（和專案自己的測試一樣），因為驗收不能碰真的 GitHub；若之後要更確定，可以在真實 repo 上保留合併一次再看清單。
- **有未存修改的保留 worktree，清理時被拒絕** — 我判斷這是既有的保護（一般變更也一樣），不算失敗；清單那一行現在也提示要先處理那些修改。
- **本機改名的情況算第 3 條的例外，不算失敗** — 第 3 條講的是維護者要求清理保留的變更；正常情況下完全做得到。改名後清不乾淨是一個少見的邊角，我列成待你決定的問題，而不是把整條判成「部分」。
