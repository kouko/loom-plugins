# 讓 loom 改用 git 判斷「哪些檔案屬於這個專案」 — 我實際試了什麼、結果如何

試跑日期 2026-09-16，在這個專案的一份全新乾淨副本上（版本 338bef0c），
我沒有參與這次改動的任何實作。

## 你要的東西，一條一條試

### 1. 在一個已經採用 loom 的專案裡，如果它的資料夾裡藏著另一個 git 工作副本，loom 的檢查器完全不會把那裡面的檔案算進來（只用安裝好的 loom-code 外掛）

- **我怎麼試的**：我另外從零建了一個跟這個專案無關的小專案（一個 README、一支程式），
  把 loom-code 外掛照使用者安裝的樣子放在那個專案之外的地方，只用那份安裝檔去跑。
  接著我在那個小專案的資料夾裡開了一個 git 工作副本，並把「另一份工作」的測試檔
  放進去，讓整個小專案裡唯一一個測試檔就在那份工作副本裡面。然後叫檢查器做結案檢查。
- **發生了什麼**：檢查器說「找不到可以執行的測試指令」而停下來 —— 它沒有把工作副本裡
  那個測試檔當成這個專案的測試。我接著在小專案自己的資料夾補了一支自己的測試檔，
  同一個檢查器立刻認出來、跑起來、通過並產出結案證明。也就是說「找不到」不是它什麼
  都看不到，而是它真的把那份工作副本排除在外。
- **佐證**：第一次 `BLOCK finalize.package-tests: no executable package command ()`；
  補上自己的測試檔後 `wrote docs/loom/2026-09-16-adopter-demo/attestation.json`（結束碼 0）。
  另外直接數過：那個小專案磁碟上共 15 個檔案，檢查器只認 6 個，工作副本裡的 4 個檔案
  一個都沒被算進去。
- **結論**：可以 —— 而且是在一個乾淨、與本專案無關的專案上，只靠安裝好的外掛做到的。

### 2. 這個專案的資料夾裡放著一個 git 工作副本時，說明裡列的那六支掃描工具全部通過，而且沒有任何一筆回報指向那份工作副本裡的檔案

- **我怎麼試的**：我在乾淨副本裡自己開了兩個臨時工作副本 —— 一個放在 Claude Code
  預設會放的位置，另一個故意放進掃描工具一定會走到的程式資料夾裡（機器上原本就有的
  那個上鎖的工作副本我完全沒碰）。然後六支工具一支一支跑。
- **發生了什麼**：六支全綠。引用檢查「15 條引用全部解得開、0 筆問題」；外掛邊界檢查
  兩個外掛都「乾淨」；舊技能名稱掃描 4 項通過；狀態措辭清單 3 項通過；CI 形狀排練
  157 項通過、0 失敗。所有輸出裡沒有出現過那兩個工作副本的名字。
- **佐證**：上述各指令的結束碼皆為 0；排練工具輸出 `FAILED (0)` / `157 passed`。
- **結論**：可以，但有一個要說清楚的窄化條件 —— 第六支（決定「這個專案的測試指令是
  什麼」那一支）在本專案裡是直接讀專案自己寫好的設定檔，根本不需要去翻資料夾，所以
  它在這裡並沒有真的被工作副本考驗到。它的翻找行為是在第 1 條那個小專案上被證明的。

### 3. 這個專案的資料夾裡放著一個 git 工作副本時，跑整包測試不會抓到那份工作副本裡的任何測試檔

- **我怎麼試的**：兩個臨時工作副本都在的情況下，跑專案自己宣告的那一行整包測試指令；
  另外再單獨做一次「只點名要收哪些測試、先不執行」的比對。
- **發生了什麼**：整包測試全綠、結束碼 0（最大的一組 1940 項通過、2 項略過），輸出裡
  完全沒有提到那兩個工作副本。比對更直接：排除工作副本時收到 1942 項測試、零錯誤；
  刻意不排除時收到 3587 項並爆出 97 個載入錯誤（同名檔案重複）。差距就是那兩份副本。
- **佐證**：整包測試指令結束碼 0；收集比對 `1942 tests collected` 對
  `3587 tests collected, 97 errors`。
- **結論**：可以。

### 4. 用 `git archive` 從同一個版本抽出一份沒有 git 的副本，那六支工具仍然跑得動，而且結論跟有 git 的版本一樣

- **我怎麼試的**：從同一個版本抽出一份完全沒有 git 紀錄的副本，在裡面把六支一支一支
  跑過，逐支跟有 git 的那份比對結論。
- **發生了什麼**：五支結論完全相同 —— 引用檢查同樣是「15 條、0 筆問題」，外掛邊界同樣
  兩個都乾淨，舊名稱掃描同樣 4 項通過，狀態措辭清單同樣 3 項通過，測試指令同樣從設定檔
  讀到同一行。連「這個專案有哪些檔案」這個答案本身都一模一樣：兩邊都是 1315 個檔案。
- **佐證**：兩邊檔案數同為 1315；兩邊選到的排練測試路徑同為 15 條。
- **結論**：大致可以，但有一條要窄化 —— 第三支（CI 形狀排練工具）在沒有 git 的副本裡
  根本啟動不了，它會說「找不到要排練的專案」並以錯誤收場。它的工作方式就是複製一份
  git 紀錄再跑，沒有 git 就沒東西可複製。我另外把改動之前的舊版本同樣抽出來試過，
  舊版在沒有 git 的副本裡也是一樣啟動不了，所以這不是這次改動弄壞的，是它本來就有的
  限制；這次改動負責的那一半（它怎麼挑要跑哪些測試）在兩邊的答案是一致的 15 條。

### 5. 一個違規的檔案，只要 git 還沒開始追蹤它、也沒有被忽略規則排除，該管它的那支工具還是會抓到

- **我怎麼試的**：我在乾淨副本裡放了五個全新、沒有被 git 追蹤、也沒有被忽略的檔案，
  每個都故意踩一支工具的規則（引用到不存在的檔案、跨外掛的連結、用了已廢除的舊技能
  名稱、多出一處被盯住的措辭、多一支排練測試）。
- **發生了什麼**：五個全部被抓出來，而且是被對應的那一支抓的。
- **佐證**：舊名稱掃描 `loom-workflow/skills/blindrun-untracked.md:1`；外掛邊界
  `escaping relative link`（FAIL 1 筆）；狀態措辭清單 `expected=0 actual=1`；引用檢查
  `file not found`（findings 1）；排練工具把那支新測試選進了待跑清單。
- **結論**：可以。第 1 條那個小專案上也再證了一次 —— 補上自己的測試檔後檢查器立刻認得。

### 6. 被忽略規則排除掉的資料夾，這六支工具一筆都不會回報

- **我怎麼試的**：把上面那五個違規檔案的內容原封不動複製一份，放進被忽略規則排除的
  資料夾裡（外加一個被逐檔指名忽略的檔案，因為有一支工具只看固定位置），再把原本那些
  沒被忽略的刪掉，然後六支重跑一次。
- **發生了什麼**：六支全綠，一筆都沒回報。直接數也一樣：那六個被忽略的檔案，一個都不在
  工具眼中「屬於這個專案」的清單裡。
- **佐證**：引用檢查回到「0 筆問題」，外掛邊界回到「乾淨」，兩支測試回到全數通過，
  排練工具選到的清單裡沒有那支被忽略的測試。
- **結論**：可以。

## 對你既有的資料做了什麼

沒有動到你原本就有的任何東西。整段試跑都在一份臨時的乾淨副本和一個臨時建立的小專案裡
進行，兩者結束後都已清掉；我自己開的兩個臨時工作副本也都移除了。機器上那個上鎖、裝著
別人未提交工作的工作副本，我從頭到尾沒有碰、沒有解鎖、沒有移除。這次改動本身不讀也不寫
任何使用者資料，只改變工具「要看哪些檔案」的判斷方式。

## 我替你決定的事

- **第 1 條的「已採用 loom 的專案」是我自己現搭的** —— 我沒有現成的第三方專案可用，
  所以從零建了一個最小的專案，把外掛放在專案之外、照安裝好的樣子呼叫。這代表「真實
  使用者的專案長什麼樣」這件事，是我假設的；假設錯的話，這一條的說服力會打折。
- **第 2、3 條我多開了一個工作副本放在程式資料夾裡** —— 只放在預設位置的話，整包測試
  根本走不到那裡，等於沒考到。多放一個才問得出真話。代價是這比一般使用者會遇到的情況
  更嚴苛，不過方向是偏嚴，不會把壞的說成好的。
- **第 4 條我判定為「部分通過」而不是通過** —— 有一支工具在沒有 git 的副本裡確實跑不
  起來。我查過改動之前也一樣，所以不算新問題，但驗收條件字面上寫的是「六支都跑得動」，
  我沒有把它四捨五入成通過。
- **審查那邊沒有交給我任何「已被駁回的重要問題」** —— 這次試跑發生在正式審查紀錄之前，
  所以這一欄是空的；如果後續審查駁回了任何重要等級以上的問題，那份清單不會自動出現在
  這裡。

## 文件用語與格式的檢查

| 文件 | 該用英文？ | 實際 | 另外綁的格式規則 | 符合？ |
|---|---|---|---|---|
| 意圖書 | 是 | 全英文 | 無 | 是 |
| 規格書 | 是 | 全英文 | 需求條列要寫成 `REQ-<編號> — <名稱>` 且編號連續 | 是（REQ-1 至 REQ-6，各自對回驗收條目） |
| 計畫書 | 是 | 有六行是中文 | 無 | 否 —— 那六行是逐字記下你在決策點說的話 |
| 審查紀錄的問題描述 | 是 | 尚不存在 | 問題標題要帶固定分類標籤 | 不適用 |
| 佐證檔（對抗測試） | 是 | 全英文 | 無 | 是（其中一支刻意用日文檔名當測試素材，屬於測試資料不是敘述） |
| 測試的說明文字 | 是 | 全英文 | 無 | 是 |
| 測試名稱 | 是 | 全英文 | 要寫成 `test_<對象>_<情境>_<預期>` | 大致符合，少數名字以主詞開頭而非以被測對象開頭 |
| 提交訊息 | 是 | 全英文 | 無 | 是 |

## 我不確定你要不要的事

- 計畫書裡那六行中文的決策紀錄要不要翻成英文？它們是你原話的逐字紀錄，翻譯會失真，
  但目前確實違反「內部文件一律英文」這條。
- 沒有 git 的副本裡跑不起來的那支排練工具，你要不要它在那種情況下改成「明確跳過並說
  原因」，而不是以錯誤收場？現在的行為跟改動前一樣，只是驗收條件字面上沒放過它。
