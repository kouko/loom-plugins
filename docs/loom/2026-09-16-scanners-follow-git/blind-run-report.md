# 讓 loom 改用 git 判斷「哪些檔案屬於這個專案」 — 我實際試了什麼、結果如何

試跑日期 2026-09-16，在這個專案的一份全新乾淨副本上（版本 dc842a23），
我沒有參與這次改動的任何實作。這份報告取代上一次（版本 338bef0c）的盲跑報告，
上一次的結論一條都沒有沿用，全部在這個版本上重新試過。之後第 4 條又在修正後的
版本 3b5eb37d 上、另一份全新副本裡重試一次（見第 4 條）；其他各條沒有重跑。

一句話總結：六條裡五條可以、第 1 條只在較窄的條件下成立。在 dc842a23 上我發現排練
工具在「確實是 git 專案、但 git 拒絕或無法運作」時也會安靜地略過；這個問題在 3b5eb37d
已修好，我重試確認現在會正確報錯。

## 你要的東西，一條一條試

### 1. 在一個已經採用 loom 的專案裡，如果它的資料夾裡藏著另一個 git 工作副本，loom 的檢查器完全不會把那裡面的檔案算進來（只用安裝好的 loom-code 外掛）

- **我怎麼試的**：我從零建了一個跟本專案無關的小專案（一個說明檔、一支程式、一支
  對抗測試程式），把 loom-code 外掛從這個版本「照出貨內容」抽一份放在小專案之外，
  只用那份去跑。接著在小專案裡、Claude Code 預設放工作副本的位置開了一個工作副本，
  模擬另一個工作階段：裡面有一支已提交的測試檔、一支還沒提交的測試檔，而小專案
  本身一支測試檔都沒有。小專案的忽略規則有把那個位置排除。然後叫檢查器做結案檢查。
  為了確認這個考法真的考得到東西，我用改動之前的外掛版本在同一個小專案再跑一次。
  最後我又另建一個「沒有把工作副本位置列進忽略規則」的小專案，同樣試一次。
- **發生了什麼**：
  - 新版檢查器說「找不到可執行的測試指令」—— 工作副本裡那兩支測試檔完全沒被當成
    這個專案的測試。舊版外掛在同一個情況下卻「看到測試檔」並選了測試指令去跑，
    結果是「沒有測試可跑」而失敗 —— 證明這個考法考得到差別。
  - 我在小專案自己的資料夾補一支測試檔並提交後，新版檢查器立刻認出來、跑過、產出
    結案證明。直接數：磁碟上 18 個檔案，檢查器只認 6 個，工作副本裡的 0 個。
  - **但是**：如果小專案沒有把工作副本的位置列入忽略規則，檢查器會在更前面就停下，
    說「請先提交功能內容」—— 因為 git 把那個工作副本當成一團未提交的新東西。改動前
    的舊版在這個情況也是一模一樣停下，所以不是這次弄壞的；但在這種專案裡，這條驗收
    「完全不算進來」並不成立。
- **佐證**：新版 `BLOCK finalize.package-tests: no executable package command ()`；
  舊版對照 `` BLOCK finalize.package-tests: `python3 -m pytest -q` exited 5 ``；
  補上自己的測試後 `wrote docs/loom/2026-09-16-adopter-demo/attestation.json`（結束碼 0）；
  檔案清單 `checker sees: 6 ... inside worktree: 0`；
  未忽略的變體（新舊版相同）`BLOCK finalize.clean-tree: commit functional content before finalizing review`。
- **結論**：部分可以 —— 只在「工作副本所在位置已被 git 忽略」的專案裡成立
  （這台機器上本專案就是這樣設定的）。沒被忽略時，檢查器會因為那個工作副本而拒絕
  結案，行為跟改動前一樣。

### 2. 這個專案的資料夾裡放著一個 git 工作副本時，說明裡列的那六支掃描工具全部通過，而且沒有任何一筆回報指向那份工作副本裡的檔案

- **我怎麼試的**：在乾淨副本裡自己開兩個臨時工作副本 —— 一個在 Claude Code 預設位置，
  另一個故意放進程式資料夾裡、沒有被忽略的地方。兩個都取自改動前的版本，並各自塞進
  會踩到每一支工具規則的內容（提到已廢除的舊技能名稱、跨外掛的連結、多一處被盯住的
  措辭、一支必定失敗的測試）。機器上原本就有的那個上鎖工作副本我完全沒碰。然後六支
  工具一支一支跑，再跟沒有工作副本時的結果比對。
- **發生了什麼**：六支全綠，跟沒有工作副本時的結果逐字相同。引用檢查「15 條檢查、
  3 條無法判定、0 筆問題」；外掛邊界兩個都「乾淨」；舊技能名稱 4 項通過；措辭清單
  3 項通過；排練 157 項通過、2 項略過。檢查器眼中的檔案數兩邊都是 1316，其中落在
  工作副本裡的是 0。所有輸出都沒有出現那兩個工作副本的路徑。
- **佐證**：六支的結束碼皆為 0；`repository_files count: 1316` /
  `files under .claude/worktrees or blindwt: 0`；
  `checked 15 / unchecked 3 / findings 0`；`157 passed, 2 skipped`。
- **結論**：可以。附帶一句：六支裡「決定測試指令」那一支，在本專案是直接讀專案自己
  寫好的設定，不需要翻資料夾，所以它真正被工作副本考驗到的是第 1 條那個小專案。

### 3. 這個專案的資料夾裡放著一個 git 工作副本時，跑整包測試不會抓到那份工作副本裡的任何測試檔

- **我怎麼試的**：在兩個工作副本都在的情況下，先把專案宣告的整包測試指令「只點名、
  不執行」逐組過一遍，數有多少測試來自工作副本；再把排除工作副本的設定拿掉做對照。
  然後實際執行整包測試兩次：兩個工作副本都在時一次、只留預設位置那個時一次。
- **發生了什麼**：
  - 點名比對：排除設定在時共收到 3197 項，來自工作副本的 0 項，零載入錯誤。拿掉排除
    設定的對照組則有 3542 項來自工作副本，並爆出 97 個載入錯誤。我塞在工作副本裡
    那兩支必定失敗的測試，在任何一次執行裡都沒出現。
  - 只留預設位置的工作副本時，整包測試全部通過、結束碼 0。
  - 工作副本放在程式資料夾裡時，整包測試**是紅的**（6 項失敗、1940 項通過）。但失敗的
    6 項不是「抓到工作副本裡的測試檔」，而是本專案自己的幾支測試在翻自己的外掛資料夾
    時，讀到了工作副本裡的舊文字。那些測試屬於說明裡明講「這次不處理」的那一類。
- **佐證**：點名比對 `TOTAL collected=3197 inside-worktree=0` 對
  `TOTAL collected=4833 inside-worktree=3542`（對照組 `97 errors`）；
  預設位置整包測試 `exit=0`；程式資料夾位置 `6 failed, 1940 passed, 2 skipped`，
  其中一例 `FAILED loom-code/scripts/test_contract_manifest.py::test_no_loom_code_review_invocation_remains - AssertionError: ['loom-code/scripts/blindwt-b/loom-code/CHANGELOG.md:911', ...`。
- **結論**：可以 —— 這條只說「不會收到工作副本裡的測試檔」，這點成立。但請知道：
  工作副本若放在程式資料夾裡，整包測試仍會因為範圍外的那幾支測試而變紅。

### 4. 用 `git archive` 從同一個版本抽出一份沒有 git 的副本，五支能在這種副本跑的工具仍然跑得動、結論跟有 git 的版本一樣；排練工具則明確回報「略過」並說明原因，而不是失敗

- **我怎麼試的**：從這個版本抽出一份完全沒有 git 紀錄的副本，六支一支一支跑，跟有 git
  的乾淨副本逐支比對。只比「全綠」不夠，所以我又在兩邊放進同一組違規檔，確認兩邊
  「紅」的結論也一樣。另外依你的要求，在真的 git 專案裡製造各種 git 出錯的情況，看
  排練工具會不會把錯誤吞掉。
- **發生了什麼**：
  - 五支結論完全相同：全綠時兩邊都是「15 條、0 筆問題」、兩個外掛都乾淨、4 項與 3 項
    通過、選到同一行測試指令，檢查器眼中的檔案數兩邊都是 1316。放進違規檔後，兩邊
    也都抓出同樣的 1 筆引用問題、1 筆跨外掛連結、1 筆舊名稱、1 筆措辭差異。
  - 排練工具在沒有 git 的副本裡印出一行「略過排練：它靠複製專案運作，需要 git 專案，
    而這個資料夾不是」，結束碼 0。
  - 在真的 git 專案裡：從專案內部紀錄資料夾執行、指定一個不是專案的位置、指向沒有
    工作區的專案 —— 這三種都照舊報錯（結束碼 2）。
  - **在 dc842a23 上的問題**：當 git 因為「資料夾擁有者不同」拒絕這個專案（容器和共用
    機器上常見），或這台機器找不到 git 程式時，排練工具在一個真的 git 專案裡也印出
    「這個資料夾不是 git 專案」並以結束碼 0 略過。改動之前，這兩種情況分別是報錯
    （結束碼 2）和直接崩潰（結束碼 1）。
  - **在修正後的 3b5eb37d 上重試**（全新暫存資料夾、全新無 git 副本、全新 git 複本）：
    - 沒有 git 的副本：照樣印出略過訊息，結束碼 0。
    - 真的 git 專案、git 因擁有者不同而拒絕：結束碼 2，訊息說「這裡或上層有 git 紀錄，
      但 git 無法解析它 —— git 有裝嗎？它接受這個專案嗎？」，沒有印出略過訊息。
    - 真的 git 專案、找不到 git 程式：同上，結束碼 2，沒有略過訊息。
    - 真的 git 專案、一切正常：照常排練，157 項通過、2 項略過，結束碼 0。
    - 我另外多試了四種：在專案的子資料夾裡且找不到 git、在一個工作副本裡且擁有者不同、
      專案紀錄損毀、在專案內部紀錄資料夾裡執行 —— 四種都是結束碼 2 且沒有略過訊息。
      損毀那一種在 dc842a23 會被略過，現在也改為報錯。
    - 在 3b5eb37d 上重比五支工具：無 git 副本與有 git 副本全綠時的結論逐字相同（同樣
      1316 個檔案、15 條 0 問題、兩個外掛乾淨、4 項與 3 項通過）；放進同一組違規檔後，
      兩邊的紅色輸出經比對完全一致。
- **佐證**：
  dc842a23 上：沒有 git 的副本 `skipping the rehearsal: it works by cloning the repository, so it needs a git repository, and this directory is not one` / `exit=0`；
  照舊報錯 ``could not determine the repository to rehearse (`git rev-parse --show-toplevel` failed)`` / `--repo is not a git repository: ...` / `--repo is a bare repository (...)`，皆 `exit=2`；
  被吞掉的情況（以 `GIT_TEST_ASSUME_DIFFERENT_OWNER=1` 模擬擁有者不同、以及把 git 從路徑移除）印出略過訊息並 `exit=0`；
  改動前同樣情況 `exit=2` 與 `FileNotFoundError: [Errno 2] No such file or directory: 'git'` / `exit=1`。
  3b5eb37d 上：無 git 副本同一句略過訊息 / `exit=0`；
  擁有者不同與找不到 git 皆為 ``could not determine the repository to rehearse: a `.git` entry exists here or above, but git failed to resolve it (`git rev-parse --show-toplevel` failed -- is git installed, and does it accept this repository?)`` / `exit=2`；
  正常專案 `157 passed, 2 skipped` / `exit=0`；
  五支工具兩邊摘要只差在排練那一行與執行秒數，違規檔的紅色輸出比對結果 `IDENTICAL`。
- **結論**：可以（在 3b5eb37d 上）。字面要求的兩件事都成立，而在 dc842a23 上發現的
  「真的專案裡 git 出錯也被略過」已修好並經我重試確認。還剩一個我沒試的邊角：無 git
  副本如果被解壓到另一個 git 專案的資料夾裡面，工具會去排練外層那個專案 —— 這跟
  改動前的行為相同，我沒有實際跑。

### 5. 一個違規的檔案，只要 git 還沒開始追蹤它、也沒有被忽略規則排除，該管它的那支工具還是會抓到

- **我怎麼試的**：在乾淨副本裡放了五個全新、未追蹤、未被忽略的檔案，各踩一支工具的
  規則：引用到不存在的檔案、跨外掛連結、舊技能名稱、多一處被盯住的措辭、一支新的排練
  測試。「決定測試指令」那一支在本專案讀設定檔、考不到，所以改在另一個小專案裡放一支
  未追蹤的測試檔來試。
- **發生了什麼**：全部被對應的那一支抓到。排練工具把那支新測試選進了待跑清單，並因為
  複製出來的專案裡沒有它而明確報錯。小專案裡，沒有測試檔時答「找不到」，放進未追蹤的
  測試檔後立刻答「偵測到測試檔」。
- **佐證**：`docs/loom/blind-a5/cite.md:3 -> loom-code/scripts/no_such_file_a5.py:3 file not found`；
  `escaping relative link: ../../outside-a5.md` / `FAIL: 1 plugin-boundary violation(s).`；
  `assert not ['loom-workflow/blind-a5-cot.md:1']`；
  `loom-design/blind-a5-anchor.md: expected=0 actual=1`；
  `ERROR: file or directory not found: loom-code/scripts/test_probes_blind_a5.py`（`exit=4`）；
  小專案 `('python3 -m pytest -q', 'detected test_*.py files')`。
- **結論**：可以。附帶一句：引用檢查只檢查被交給它的文件，而持續整合那邊是用
  「git 已追蹤的文件」來開清單，所以一份還沒加進 git 的新文件，要等加進去之後才會在
  那裡被檢查。

### 6. 被忽略規則排除掉的資料夾，這六支工具一筆都不會回報

- **我怎麼試的**：把第 5 條那五個違規檔原封不動搬進被忽略規則排除的資料夾（排練測試
  那支因為工具只看固定位置，改用逐檔指名忽略），再跑六支。「決定測試指令」那支在小專案
  裡另放一支測試檔到被忽略的資料夾來試。
- **發生了什麼**：六支全綠、一筆都沒回報，結果跟完全沒放違規檔時相同。檔案清單裡那些
  被忽略的檔案一個都沒有。小專案裡，測試檔只在被忽略的資料夾時，答案是「找不到」。
- **佐證**：`checked 15 / unchecked 3 / findings 0`；`OK: loom-code is filesystem-boundary clean.`；
  `4 passed`、`3 passed`、`157 passed, 2 skipped`（皆 `exit=0`）；
  `ignored plants in file list: 0`；小專案 `(None, '')`。
- **結論**：可以。

### 上次修掉的問題：巢狀工作副本會讓「找不到檔案」的引用問題消失

- **我怎麼試的**：寫一份引用某個檔案的文件，而那個檔案只存在於巢狀工作副本裡、專案
  本身沒有。同一個情境用這次的版本和修正前的版本各跑一次。再換幾種放法：工作副本放在
  沒被忽略的位置、一個普通的 git 複本放在沒被忽略的位置、一個普通的 git 複本放在被忽略
  的位置。
- **發生了什麼**：修正前的版本在前三種放法下都把問題吞掉（變成「無法判定」、結束碼 0）；
  這次的版本三種都正確回報「找不到檔案」、結束碼 1 —— 修正確實有效。但第四種：一個
  普通的 git 複本放在被忽略的位置時，兩個版本都仍然吞掉，只標成「無法判定」。
- **佐證**：這次版本 `docs/loom/blind-cite/citing.md:3 -> docs/loom/blind-cite/only-elsewhere.md:1 file not found` / `exit=1`；
  修正前 `checked 0 / unchecked 1 / findings 0` / `exit=0`；
  被忽略位置的普通複本（兩版相同）`NOTE: nothing verified — every citation found was unresolvable (...)` / `exit=0`。
- **結論**：修正有效。剩下的那一種，符合說明裡「被忽略的東西變成不檢查」的寫法，
  所以不算違反你確認過的範圍；但它跟「工作副本放同一個位置會被抓到」前後不一致，在你的
  電腦上是綠的、在持續整合上會是紅的。

## 對你既有的資料做了什麼

沒有動到你原本就有的任何東西。整段試跑都在臨時的乾淨副本、臨時抽出的無 git 副本、
和我自己新建的幾個小專案裡進行。我在本專案開的四個臨時工作副本都已移除；機器上那個
上鎖、裝著別人未提交工作的工作副本，我從頭到尾沒有碰、沒有解鎖、沒有移除。有兩件事
要說清楚：第一，上一次盲跑聲稱「已清掉」的臨時資料夾其實還留在暫存區，我第一次試時
誤用到其中幾個，發現後已全部改在全新的資料夾重做，報告裡的結果都來自重做的那一次；
第二，這次我建的小專案、無 git 副本和第 4 條重試用的 git 複本也還留在系統暫存區（刪除整個資料夾的指令被安全
防護擋下），不在你的專案裡，也不影響任何東西。這次改動本身不讀也不寫任何使用者資料，
只改變工具「要看哪些檔案」的判斷方式。
