# Optional long-term preservation

Use this reference on demand after a change has merged into main and cleanup
has succeeded, or when explicitly asked about research from an earlier merged
change. Preserve the owning task, its authorization and project originals.
This is an optional external-write proposal, not another station or completion
gate. No background release watching or automatic synchronization is implied.

## Establish eligibility and provenance

Follow the finishing command's printed cleanup destination before further
filesystem work. Verify the exact change's merge into main from repository or
hosting evidence and identify a stable merged revision. A closed intent,
publication, green checks or a locally completed task alone proves no merge.
If merge or cleanup is unverified or failed, defer the proposal and report the
missing evidence without undoing the merge or blocking the original task.

Inspect relevant research records and choose only findings with enduring or
cross-repository value. Release-dependent claims require the applicable release
evidence; defer those claims when absent. Independently supported source findings
may be proposed with their actual version and source scope. Do not promise to
notice a later release while idle. If nothing qualifies, return to the owning
task without an export proposal.

## Prepare a concrete candidate before asking

Prepare the proposed note content with its question, applicable conditions,
findings, evidence limits and project provenance. Include repository identity,
the stable revision and ordinary Markdown links to pinned research originals
and source references. Keep the project originals in place. A project draft
uses working Markdown links from its current location even when the Vault
destination is unresolved; code-formatted paths alone do not provide navigation.
Adapt and verify the links again for the authorized destination before copying.
Do not invent a remote URL or imply a proposed note has already been saved.

Discover destinations only through available capabilities and within the task's
authorized filesystem scope; read-only discovery does not expand that scope.
When an official Obsidian CLI is available, use `obsidian:obsidian-cli` when
installed and inspect local CLI help/version before choosing supported
Vault-query syntax. Do not guess commands or a home-folder Vault path.
Discovery is read-only; do not
install tools or start a service for it. A detected Vault or folder name is
neither a destination preference nor write consent. With several results,
present candidates and let the user select. Without the CLI, use a user-supplied
destination or present an explicitly unsaved candidate with the destination
unresolved.

Present the actual candidate content (or a reviewable draft), its provenance,
proposed destination path when known, and exact content scope together. Ask for
explicit authorization of that instance's destination and scope. If the
destination is unresolved, request it together with approval of the prepared
scope. Never ask only an abstract permission question. Prior implementation,
publication, merge, export or general Vault permissions do not authorize this
copy; ask again for each new preservation instance. Refusal or no response
leaves the candidate unsaved and original task completion unaffected.

## Save only the authorized copy

Immediately before writing, recheck the user's instance-specific permission,
target path and scope. Check for an existing note; overwriting it needs separate
explicit authorization. Write only the agreed content to the agreed destination
using an available authorized mechanism. Do not broaden this into a batch,
reorganization, deletion or synchronization. If writing is prohibited or fails,
return the explicitly unsaved candidate and the missing saved artifact.

Read back the actual saved note's substantive content and copy provenance,
and resolve its evidence links from the saved destination before calling it
saved. Hashes, link existence and write success alone do not inspect its body.
Report the confirmed path, checks actually performed and any remaining limits.
Distinguish this saved-copy result from research correctness, merged/released
state, isolated-loader evidence and installed-host behavior; one does not prove
the others. An untested host remains untested.
